# Backlog

Funcionalidades evaluadas durante el desarrollo y pospuestas conscientemente para después del MVP. Cada entrada documenta el motivo del corte, para no perder el razonamiento de la decisión.

## Post-MVP

- **Evaluar qué información de INDEC agrega valor real, una vez cerrada la etapa de BCRA.** El MVP (calculadoras de ajuste por inflación, comparación dólar/tasas y ajuste de alquileres) se construye 100% con variables del BCRA — ver decisión 005 en `DECISIONS.md`. INDEC queda pospuesto, no descartado: cuando esté cerrado el desarrollo con BCRA, evaluar si vale la pena sumar la API de series de datos.gob.ar para algo que el BCRA no cubre (ej. desglose de IPC por rubro/categoría, canasta básica, EMAE, series regionales). Requiere primero buscar los IDs de series relevantes en el catálogo de datos.gob.ar, que a diferencia del BCRA no tiene un endpoint autodescriptivo de variables. *(evaluado: 2026-07-27)*

- **Sumar el IPCBA (Ciudad de Buenos Aires) como índice de inflación alternativo/independiente para contrastar.** Se investigaron fuentes de medición de inflación distintas a BCRA/INDEC para poder comparar. PriceStats/"Inflación Verdadera" (metodología propia, alta frecuencia) no tiene API pública/gratuita vigente — hoy es un producto comercial. "Inflación Congreso" (promedio de consultoras privadas) tampoco tiene API, se publica como comunicado de prensa. ArgentinaDatos y ArgenStats se descartaron: son wrappers de terceros que re-publican el IPC oficial de INDEC, no una medición distinta. El hallazgo viable: el **IPCBA**, publicado por el IDECBA (organismo de la Ciudad de Buenos Aires, no INDEC ni BCRA), con metodología y canasta propias, accesible vía la misma API de series de datos.gob.ar (serie verificada: `193.2_NIVEL_GENERAL_2021_0_13_2`, índice de nivel base 2021=100 — no requiere reconstrucción, el coeficiente sale directo de `índice(destino)/índice(origen)`). Sería una **segunda línea de referencia específica** en la calculadora de ajuste por inflación (ej. "según IPC nacional (BCRA)" vs. "según IPCBA (CABA)"), útil en especial para quien ajusta valores atados a la Ciudad de Buenos Aires (alquileres, gastos locales). Caveats a resolver antes de implementar: (1) mide solo precios de CABA, no es comparable 1 a 1 con la inflación nacional que usa el resto del dashboard — la UI tiene que dejar esto clarísimo para no inducir a error; (2) el último dato visto en la verificación fue de enero 2026, con varios meses de rezago respecto al dato de BCRA (junio 2026) — confirmar la cadencia real de actualización antes de prometerlo como dato "al día". *(evaluado: 2026-07-27)*

- **Sumar RIPTE como método comparativo en la sección salarial.** La sección de evolución salarial usa el Índice de Salarios de INDEC (ver decisión 008 en `DECISIONS.md`). RIPTE (Remuneración Imponible Promedio de los Trabajadores Estables) es otra referencia salarial muy usada en Argentina en la práctica — se usa habitualmente para ajustar cuotas de juicios laborales y algunos contratos de alquiler — pero la publica la Secretaría de Seguridad Social (ANSES), no INDEC ni BCRA. Mismo tratamiento que se le dio al IPCBA como alternativa de inflación: queda pospuesto como una segunda referencia posible, no como reemplazo. Pendiente antes de implementar: confirmar si la Secretaría de Seguridad Social publica RIPTE en datos.gob.ar con un ID de serie consultable (no se investigó todavía, a diferencia de IPCBA que ya se verificó funcionando). *(evaluado: 2026-07-27)*

- **Tests de componentes (React Testing Library) y manejo de errores en la UI.** Se sumó Vitest para la lógica pura de `src/lib/` (ver decisión 009 en `DECISIONS.md`), pero no hay todavía tests de los componentes React ni de casos de error mostrados en pantalla (fetch fallido, mes fuera de rango, input inválido). Tiene sentido atacarlo junto con una revisión general de manejo de errores en la UI, no antes — hoy los componentes manejan el error mínimo (mensajes de "no se pudo cargar"/"no hay datos") pero sin una estrategia consistente ni tests que la verifiquen. *(evaluado: 2026-07-27)*

- **Arreglar el deploy en GitHub Pages — hoy muestra la página en blanco.** Se probó el deploy y quedó en blanco. Diagnóstico verificado con `curl` contra `https://gogoroisler.github.io/dashboard-bcra-indec-react/`: hay dos problemas distintos, no uno solo.
  1. **Pages está publicando el código fuente crudo, no el build.** El HTML publicado tiene `<script src="/src/main.tsx">` — un archivo TypeScript/JSX que ningún navegador puede ejecutar. Esto pasa porque la fuente de Pages está configurada como "la rama `main` tal cual", sin ningún paso que corra `npm run build` antes de publicar.
  2. **Aunque se publicara el build real, también rompería.** `npm run build` genera rutas absolutas desde la raíz del dominio (`/assets/index-xxx.js`, `/favicon.svg`), pero el sitio vive en un subpath (`gogoroisler.github.io/dashboard-bcra-indec-react/`, no en la raíz de `gogoroisler.github.io`) — esas rutas apuntarían mal (404) y la página quedaría en blanco igual. Hace falta configurar `base: '/dashboard-bcra-indec-react/'` en `vite.config.ts`.

  La solución recomendada (no implementada todavía): un workflow de GitHub Actions que corra `npm run build` en cada push a `main` y publique el resultado automáticamente (`actions/deploy-pages`), en vez de depender de un build manual. Requiere además cambiar la fuente de Pages a "GitHub Actions" en Settings → Pages (un paso manual de un click, no se puede hacer sin `gh` CLI o acceso a la UI de GitHub). *(evaluado: 2026-07-27 — no se trabaja todavía, según lo acordado)*
